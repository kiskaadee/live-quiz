### 2.2 Accepted `B2.4` Framing Constraints (`USER_EXPLICIT`, step `849`)

In `step 849`, the user decomposed `B2.4` into five subdecisions (`B2.4.1`–`B2.4.5`, tracked as `S1-01`–`S1-05`) and established four binding framing constraints:
1. `schema_version` is a top-level field of `questionnaire.json` and is therefore covered by $H_q = \operatorname{SHA256}(\operatorname{JCS}(Q))$.
2. Changing `schema_version` changes $H_q$, which under `BL-01`/`BL-02` requires registering a new `assessment_id` with no version lineage.
3. Registered $(Q, R)$ pairs are never migrated or rewritten in place.
4. Cosmetic UI improvements and internal code refactoring must not require a new `schema_version`.

### `S1-02` — `B2.4.2` (Semantic Immutability Boundary)
| Field | Description |
| :--- | :--- |
| **Task ID** | `S1-02` |
| **Decision ID** | `B2.4.2` |
| **Decision question** | Which changes to questionnaire interpretation or rendering require a new `schema_version` versus qualifying as contract-preserving implementation improvements? |
| **Already-settled constraints** | `S1-01` (`B2.4.1`) four-pillar unified contract scope, `BL-01`/`BL-02` pair immutability, `B2.1`/`BL-03` raw-JSON $H_q$, and `step 849` framing constraint (cosmetic changes and internal refactoring do not require a new contract version). |
| **Approved decision** | Adopt **Option 1: Pillar-Based Outcome & Specification Criterion**. A new `schema_version` is required whenever the **normative questionnaire contract** changes in any of the four `S1-01` pillars: (1) document structure and validation constraints, (2) semantics of omitted optional fields, (3) assessment-significant runtime interpretation, and (4) questionnaire-defined response and export semantics. The classification criterion is a change to the **normative contract**, not merely a change in observed implementation behavior. Implementation changes that restore conformance to an existing, sufficiently specified contract do **not** require a new `schema_version`—including corrections to structural validation, defaults, runtime behavior, and export behavior when the existing specification already defines intended behavior. Conversely, resolving genuine specification ambiguity by selecting a different interpretation changes the normative contract and **requires** a new `schema_version`. Contract-preserving implementation improvements may retain the existing version, including: cosmetic presentation and styling changes; accessibility improvements preserving equivalent information and task constraints; internal refactoring and equivalent dependency or renderer upgrades; and spec-compliance bug fixes. Two attempts sharing a `schema_version` are governed by the same normative questionnaire contract, which does not by itself establish that their actual execution environments or implementation builds were identical; engine implementation provenance, if required for historical execution reproducibility, is separate from questionnaire contract versioning. |
| **Modification delta vs. `step 850`** | Anchored the immutability boundary directly to changes in the **normative questionnaire contract** across the four `S1-01` pillars rather than observed implementation behavior alone; clarified that spec-compliance bug fixes encompass structural validation, defaults, runtime behavior, and export behavior when sufficiently specified, whereas resolving genuine specification ambiguity requires a new `schema_version`; explicitly decoupled contract equivalence (`schema_version`) from engine build/execution-environment provenance. |
| **Rejected alternatives & rationale** | • **Strict presentation- & renderer-locked boundary:** Rejected under `step 849` because treating cosmetic UI, accessibility, or equivalent renderer updates as contract-breaking causes unnecessary version churn and retirement pressure (`S1-04`).<br>• **Structural-validation-only boundary:** Rejected because omitting default, runtime, and export semantics contradicts `S1-01` and allows silent behavioral drift for an identical $H_q$ under `B2.1`. |
| **Provenance** | `USER_EXPLICIT` (approved `2026-11-15`; originating proposal `step 850`) |

### `S1-03` — `B2.4.3` (Defaults and Explicit Configuration)
| Field | Description |
| :--- | :--- |
| **Task ID** | `S1-03` |
| **Decision ID** | `B2.4.3` |
| **Decision question** | Which behavioral settings in `questionnaire.json` must be explicitly authored, and which optional fields may be omitted with frozen semantics under a contract version? |
| **Already-settled constraints** | `BL-03` (standalone `questionnaire.json` may omit `assessment_id`), `BL-04` (self-contained journal snapshot), `B2.1` (Pydantic defaults are never injected into $H_q$), `S1-01` (`B2.4.1`), and `S1-02` (`B2.4.2`). |
| **Approved decision** | Adopt **Option 1: Explicit Behavioral Authoring & Strictly Bounded "Absent / Not Applicable" Optionality**. All assessment-significant configuration must be explicitly represented in `questionnaire.json`, including: (1) contract identifier (`schema_version`), (2) timing policy (including explicit timed or untimed behavior), (3) question interaction primitive and applicable behavioral constraints, (4) author-declared learning objective references, and (5) other questionnaire-level or question-level rules affecting administration, interaction, or response capture. Omission is permitted only when the normative contract defines a stable, unambiguous absence or not-applicable meaning that introduces no hidden behavioral policy—for example, `assessment_id` omitted for standalone execution and required for registered assessments (`BL-03`), optional stimulus and presentation attachments omitted to indicate their absence (even if present they affect behavior), and optional grouping metadata omitted to indicate no additional grouping or scenario context. The original parsed JSON tree remains authoritative for $H_q$; internal model defaults must not alter the authored representation used for hashing.
